01 · The question this page answers

"Can I set hash partitioning on an S3 Table?"

No — and the reason is worth ten minutes of any lecture. S3 Tables is a storage engine and an Iceberg REST catalog. It manages metadata definitions and physical file maintenance. Every shuffle mechanism people ask about happens somewhere else entirely: inside a compute engine, in worker memory, before a single Parquet file is written.

What S3 Tables fixes for you

File size

Small files from a trickle-feed stream get merged toward the 512 MB target, continuously, without you scheduling anything.

What it half fixes

File contents

Only if you declared a sort_order. Then auto compaction switches to sort strategy and clusters rows on rewrite. Without one, it just bin-packs.

What it never fixes

Layout decisions

Partitioning on a high-cardinality column, a join key nobody filters on, a missing sort order. Those stay yours.

02 · Hash partitioning

Route by key — correctness, not balance

Compute hash(key) % N and send the row there. Every row with the same key lands on the same machine, guaranteed — which is exactly what makes groupBy and join correct. Spark does this automatically; you almost never call it by name.

Where it runs

Executor memory, mid-job

A network exchange between two stages. Nothing about it is persisted anywhere.

What reaches S3 Tables

Uneven file sizes

Severe skew on a key produces one enormous Parquet file and many small ones. The storage layer just receives them — and that straggler shows up again on every future read.

PySparkimplicit almost always
# all of these hash-partition under the hood
df.groupBy("region").agg(F.sum("amount"))
df.join(other, "customer_id")
Window.partitionBy("region")

# explicit only when you reuse the same partitioning repeatedly
df = df.repartition(200, "customer_id").cache()
SKEW
Confirm AQE is on before hand-tuning anything — it splits skewed partitions at runtime. If skew survives that, salt the key: aggregate on key_salt, then re-aggregate on key. Buying a bigger cluster hides this; it does not fix it.
03 · Range partitioning

The only one that preserves order

Hash scatters adjacent values across unrelated partitions. Range gives each partition a contiguous band, so partition 0's maximum sits below partition 1's minimum and the concatenation is globally sorted. Spark must first run a sampling job to pick boundaries — that is the mysterious extra stage before a big orderBy.

Where it runs

A sampling pass, then a shuffle

Costs a scan plus an exchange — the most expensive of the seven.

What reaches S3 Tables

Aligned min/max bounds

Because file value-ranges line up with global order, Iceberg manifests prune sharply on that column for every downstream query. This is the one shuffle whose benefit persists into storage.

PySparkand the free alternative
df.repartitionByRange(64, "order_amount")   # explicit
df.orderBy("order_amount")                    # implicit: sample + range shuffle + local sort
df.sortWithinPartitions("order_amount")      # NO shuffle at all
BETTER
On S3 Tables there is a cheaper way to get the same clustering permanently: declare WRITE ORDERED BY on the table. auto compaction then applies the sort strategy on every rewrite, so the storage layer maintains the clustering for you instead of you paying a range shuffle in every job.
04 · Round-robin

Deal the rows out like cards

No key, no hash, no order — each row goes to the next partition in turn. Perfectly even sizes, zero locality. It is the anti-skew hammer for map-only work.

Reach for it

Heavy per-row work, no aggregation

Parsing, scoring, an inference pass. Even task sizes are all that matter and locality is irrelevant.

What reaches S3 Tables

Uniform files, useless statistics

Every file ends up holding a mix of every key, so min/max bounds span everything and Iceberg can prune nothing. Even sizes, zero pruning.

PySparkthe missing argument is the whole difference
df.repartition(400)              # round-robin — even, no locality
df.repartition(400, "region")    # hash — locality, uneven sizes
05 · Coalesce vs repartition

The one that moves nothing — and its trap

coalesce(N) merges adjacent partitions in place, on the machines already holding them. No network, nearly free. It can only shrink — and it has one failure mode that costs people hours.

06 · Broadcast

The best shuffle is the one you delete

If one side of a join is small, don't partition either side — copy the small table to every executor and join locally. The exchange disappears. It is the largest single win available on a star-schema join, and it is invisible to storage: S3 Tables just serves file references to both sides.

PySparkbe explicit when you already know
from pyspark.sql.functions import broadcast
facts.join(broadcast(dims), "dim_id")

# AQE converts sort-merge to broadcast at RUNTIME once it sees real sizes,
# but it cannot help if the estimate was wrong before the first stage ran.
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", "104857600")  # 100 MB
OOM
Broadcasting something that is not small is worse than not broadcasting: the small side is collected to the driver first. A 4 GB "small side" kills your driver with an error that never mentions the word broadcast.
07 · Write partitioning

The first of the two that S3 Tables actually stores

Shuffle partitioning lasts one job. A partition transform lasts until someone rewrites the table — it is recorded in the Iceberg metadata and every future query inherits it. This is a real S3 Tables concern, unlike everything in chapters 02–06.

08 · Bucketing

Pre-shuffle once, join for free afterwards

The second thing S3 Tables really stores. bucket(N, col) writes data already hash-partitioned on disk. Two tables bucketed identically on the same key can be joined with no shuffle at all — you paid the shuffle once, at write time.

The condition

Same column, same N

Both sides must share the exact bucket column and bucket count. Different counts and the engine shuffles anyway, silently — you get the storage rigidity with none of the benefit.

The rigidity

Changing N is a rewrite

Suits stable, high-traffic tables where the same join runs many times a day. Iceberg at least lets you evolve the spec without rewriting history — new data uses the new bucketing, old data keeps the old.

Declared in the table, not the jobthis is the metadata S3 Tables holds
-- Athena
CREATE TABLE orders (…)
PARTITIONED BY (day(order_timestamp), bucket(128, user_id))
TBLPROPERTIES ('table_type'='iceberg');

-- Spark: evolve it later without rewriting history
ALTER TABLE … ADD PARTITION FIELD bucket(64, user_id);

Who owns what

MechanismExecutes inPersisted?What S3 Tables sees / does
HashEngine — executor memoryNoReceives the resulting files. Skew arrives as uneven file sizes.
RangeEngine — sampling pass + exchangeNoFile value-ranges align with global order, so manifest min/max pruning gets sharper.
Round-robinEngine — exchangeNoEven file sizes, but statistics span everything so nothing prunes.
CoalesceEngine — local merge, no networkNoControls how many Parquet files land. Compaction would fix it anyway.
BroadcastEngine — DAG optimisationNoNothing. It serves file references to both sides; the join happens in memory.
Write partitioningIceberg spec — the catalogYesStores the transform. Every future query inherits the pruning — or the mistake.
BucketingIceberg spec + engineYesStores the bucket spec, enabling shuffle-free joins between identically bucketed tables.
ASK
The diagnostic order, before you touch any partitioner: ① Am I reading too much — check PartitionFilters. ② How many shuffles are there — can one be broadcast away? ③ Is it skewed — is max task time 40× the median? ④ Are there fewer tasks than cores? Only then reach for a partitioner.
LAST
Notice what is not on this page: buying a bigger cluster, and changing an S3 Tables setting to fix a slow query. Neither works. The first hides a layout problem expensively; the second is a category error.
