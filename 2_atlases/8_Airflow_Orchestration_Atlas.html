01 · The boundary

An orchestrator, not an engine

Every confusion about Airflow comes from expecting it to do work. It does not. Airflow is a scheduler with a dependency graph and a state machine. It calls other systems — EMR, Glue, Athena, Redshift, a shell — waits, records the result, and decides what to call next. The heavy lifting happens elsewhere, and if it happens inside Airflow's own worker you have made a design mistake.

Airflow IS

Scheduling and dependency

  • cron and data-driven scheduling
  • a DAG of tasks with explicit ordering
  • retries, timeouts, alerting, backfill
  • one UI showing every run of every pipeline
Airflow IS NOT

Compute or transport

  • not a Spark cluster — it submits to one
  • not an ETL tool — it orders ETL steps
  • not a queue — XCom carries ids, not data
  • not real-time — it schedules in minutes, not milliseconds
Airflow REPLACES

The thing you had before

  • cron jobs on a box someone forgot about
  • a bash script that calls five other scripts
  • "Raj runs it every morning"
  • a Step Functions state machine that grew a UI
02 · Architecture

03 · The lifecycle

The life of one DAG run

The concept that trips up every newcomer: a run is for a data interval, and it starts after that interval ends. A daily DAG scheduled at midnight runs on the 3rd to process the 2nd. Its logical date is the 2nd. Every timestamp you template into a path or a query comes from the interval, never from the wall clock.

3.x
A manually triggered run has no logical date in Airflow 3. {{ ds }} is not None — it is undefined, and a @task that declares ds as a parameter fails with "missing argument". Lab DAG 01 shows the idiom that works for both: {{ (dag_run.logical_date or dag_run.run_after) | ds }}. This was found by running the lab, not by reading docs.
3.x
Airflow 2 called this execution_date, and half the internet still does. Airflow 3 removed it. The names are logical_date, data_interval_start and data_interval_end. Code copied from a 2022 blog post will fail to parse. Chapter 09 lists every rename.

05 · The integration

The pipeline you already built, orchestrated

This is lab DAG 04. It runs the six iceberg_deep scripts as bronze → silver → gold — and the point is that not one line of the Spark scripts changes between running on your laptop and running on EMR Serverless. Airflow decides where; the script is the same.

the one operator that matters most for this courseEmrServerlessStartJobOperator, from the amazon provider
from airflow.providers.amazon.aws.operators.emr import EmrServerlessStartJobOperator

silver = EmrServerlessStartJobOperator(
    task_id="silver_02_commits",
    application_id="00fabc…",                 # the EMR Serverless app, created once
    execution_role_arn="arn:aws:iam::…:role/EmrLabRole",
    job_driver={"sparkSubmit": {
        "entryPoint": "s3://bucket/labs/iceberg_deep/02_commits_time_travel.py",
        "sparkSubmitParameters": "--conf spark.executor.memory=4g "
                                 "--py-files s3://bucket/labs/iceberg_deep/common.py"}},
    configuration_overrides={"monitoringConfiguration": {
        "s3MonitoringConfiguration": {"logUri": "s3://bucket/emr-logs/"}}},
    wait_for_completion=True,
    deferrable=True,       # the triggerer polls; no worker is held for 20 minutes
    retries=1, retry_delay=timedelta(minutes=2),
)
06 · Local vs managed

What changes when you move to MWAA

Nothing in the DAG. Everything around it. MWAA is 100% upstream Apache Airflow with the operations taken away from you — which is exactly what you want in production and exactly what gets in your way while learning. Practise on the compose stack, deploy to MWAA.

07 · Not the same thing

Airflow vs dbt

They are asked about together because they appear together. Airflow orders work across systems; dbt defines transformations inside one. A mature stack uses both: Airflow triggers dbt run as one task among many.

Apache Airflowdbt
CategoryOrchestrator / workflow schedulerTransformation framework
Unit of workA task in a DAG — any callable, any systemA model — one SQL SELECT → one table/view
Where compute runsElsewhere: EMR, Glue, Athena, Redshift, LambdaInside the engine it connects to
SchedulingCore: cron, Assets, backfill, retries, SLAsNone — needs Airflow, dbt Cloud, or cron
DependenciesExplicit edges between tasksInferred from ref() between models

LineageTask-level, cross-systemModel/column-level, inside SQL

TogetherAirflow runs dbt run / dbt test as tasks — via BashOperator or the Cosmos provider that renders each dbt model as its own Airflow task
08 · The AWS-native alternatives

When you would not use Airflow

Atlas 7 showed that EventBridge can trigger an EMR job with no Lambda. So why Airflow? Because a trigger is not a pipeline. The moment you need step B to wait for step A, retry on failure, skip on a condition and show a human what happened, you are rebuilding Airflow badly.

needEventBridge SchedulerStep FunctionsAirflow / MWAA
Run one job on a cronBest. No idle cost, no infra.OverkillOverkill — but fine if Airflow already exists
A → B → C with retriesNo — one target per scheduleGood. State machine, native retriesGood. Plus a UI, backfill, sensors
Wait for a file, then runVia S3 → EventBridge ruleNeeds a Lambda poller or callbackA sensor — one line
Backfill last monthNo conceptManual, per executionairflow backfill — built in

Vendor lock-inAWSAWSOpen source — same DAG runs on GCP Composer, Astronomer, your own k8s
RULE
One job, one schedule → EventBridge Scheduler. A handful of steps, all AWS, no humans watching → Step Functions. A team's worth of pipelines with dependencies, backfills and an on-call rota → Airflow. The mistake is choosing by familiarity rather than by that list.
