A · Define

The DAG itself

Five parameters carry almost all of the meaning. Get start_date and catchup wrong and you will create 400 runs on a Friday evening.

01

@dag / DAG

airflow.sdk

The container. The decorator form and the context-manager form are equivalent; the decorator is what new code uses.

pythonlab 01 (DAG) · lab 02 (@dag)
from airflow.sdk import dag, task, DAG

@dag(dag_id="nightly_iceberg", schedule="0 2 * * *", start_date=datetime(2026, 9, 1), catchup=False)
def nightly():
    ...
nightly()                          # the call registers it; forgetting this = DAG never appears

with DAG(dag_id="nightly_iceberg", schedule="0 2 * * *", ...) as dag:
    ...

Gotcha. dag_id must be unique across the whole deployment; the file name does not matter. Two files defining the same id → one silently wins.

02

schedule=

parameter

When runs are created. Cron string, preset, timedelta, a list of Assets, or None.

pythonall valid
schedule="0 2 * * *"            # cron, UTC unless the DAG sets a timezone
schedule="@daily"               # preset: @hourly @daily @weekly @monthly
schedule=timedelta(hours=6)     # every 6h from start_date
schedule=[silver_orders]        # run when this Asset is updated (block 22)
schedule=None                   # manual or triggered only

Gotcha. It was schedule_interval= in Airflow 2. That keyword no longer exists; every 2.x tutorial you copy needs this one rename.

03

start_date + catchup

parameters

start_date is the first data interval. catchup=True (the default!) creates a run for every interval between it and now the moment the DAG is unpaused.

pythonlab 06 does this on purpose
start_date=datetime(2026, 1, 1), schedule="@daily", catchup=True    # unpaused on Sep 2 → 244 runs, now
start_date=datetime(2026, 1, 1), schedule="@daily", catchup=False   # only the latest interval runs

Gotcha. Use a fixed date, never datetime.now(), in production — a moving start_date confuses the scheduler. Lab 06 uses now() - 7 days only so the demo always shows exactly seven catch-up runs.

04

default_args

parameter

A dict applied to every task in the DAG. This is where retries, owner and callbacks live so no task forgets them.

pythonlab 04, 08
default_args={
    "owner": "data-eng",
    "retries": 2,
    "retry_delay": timedelta(minutes=2),
    "retry_exponential_backoff": True,
    "execution_timeout": timedelta(hours=1),
    "on_failure_callback": page_on_call,
}

Gotcha. A task-level argument overrides the default silently. If one task has retries=0 in its constructor, the DAG default of 2 does not apply to it.

05

max_active_runs · max_active_tasks · tags

parameters

Concurrency at the DAG level, and the labels the UI filters on.

pythonlab 04
max_active_runs=1        # two nightly runs must never overlap — they'd write the same partitions
max_active_tasks=4       # at most 4 tasks of this DAG running at once, across all its runs
tags=["iceberg", "nightly", "tier-1"]

Gotcha. max_active_runs=1 plus catchup=True means a backfill runs strictly one day at a time. Usually what you want for a pipeline that overwrites partitions; not what you want for one that only reads.

B · Do

Tasks and how they connect

06

@task

airflow.sdk

TaskFlow. The function is the task; its arguments are upstream XComs; its return value is this task's XCom. How 90% of new DAGs are written.

pythonlab 02
@task
def extract() -> dict:
    return {"rows": 1_240_331, "path": "s3://…/raw/2026-09-02/"}

@task(retries=3)
def transform(payload: dict) -> int:      # payload IS extract()'s XCom
    return payload["rows"]

transform(extract())                    # calling wires the dependency

Gotcha. The function body runs on a worker with no Spark, no big memory. Return an id or a path, never a DataFrame. Context values (ds, data_interval_start) are injected by parameter name if you declare them.

07

BashOperator

providers.standard.operators.bash

Run a shell command. The universal escape hatch: spark-submit, dbt, aws cli, a script.

pythonlab 01, 04
from airflow.providers.standard.operators.bash import BashOperator

run = BashOperator(
    task_id="silver",
    bash_command="cd /opt/airflow/work && python /opt/airflow/labs/iceberg_deep/01_anatomy.py",
    env={"RUN_DATE": "{{ ds }}"},              # templated; the script reads os.environ
    append_env=True,
)

Gotcha. A command ending in a space and pointing at a .sh file is treated as a Jinja template file and fails with a cryptic error. Either drop the trailing space or use bash script.sh.

08

PythonOperator · EmptyOperator

providers.standard.operators.python / .empty

The classic way to run Python (pre-TaskFlow), and a do-nothing node used as a join point or a named marker in the graph.

pythonlab 01, 02
from airflow.providers.standard.operators.python import PythonOperator
from airflow.providers.standard.operators.empty import EmptyOperator

hello = PythonOperator(task_id="hello", python_callable=my_fn, op_kwargs={"n": 3})
join  = EmptyOperator(task_id="join", trigger_rule="none_failed_min_one_success")

Gotcha. DummyOperator is the Airflow 1/2 name. Gone.

09

>> · chain() · lists

airflow.sdk

Dependencies. >> is "then"; a list on either side fans out or in.

pythonlab 01, 02, 04
a >> b >> c                     # linear
a >> [b, c] >> d                # fan out to b and c, both must finish before d
from airflow.sdk import chain
chain(a, [b, c], [d, e], f)     # pairwise: b>>d, c>>e — different from the line above

Gotcha. [b, c] >> [d, e] is not allowed directly (list to list). Use chain or cross_downstream.

10

TaskGroup

airflow.sdk

A collapsible box in the graph with its own prefix on task ids. Replaces SubDAGs, which are removed in 3.x.

pythonlab 04
from airflow.sdk import TaskGroup

with TaskGroup("silver") as silver:
    anatomy = spark_step("01_anatomy")       # task_id becomes silver.01_anatomy
    commits = spark_step("02_commits")
    anatomy >> commits
bronze >> silver >> gold                    # groups chain like tasks

Gotcha. Purely organisational — no scheduling semantics. A group does not retry as a unit.

11

trigger_rule

parameter on every task

When a task may run given its parents' final states. Default all_success: one skipped or failed parent and the child never runs.

pythonlab 02, 08
trigger_rule="all_success"                   # default
trigger_rule="none_failed_min_one_success"   # the join after a branch
trigger_rule="all_done"                      # cleanup: run whatever happened
trigger_rule="one_failed"                    # an alert task
trigger_rule="all_failed" / "one_success" / "none_skipped" / "always"

Gotcha. The most common "my DAG stops for no reason": a branch skipped one path, and the join downstream still has all_success. Skipped propagates.

C · Connect

Values, secrets and config

12

XCom

implicit with @task; explicit with ti.xcom_pull

Small values between tasks, stored in the metadata DB. Return values from @task are XComs automatically.

pythonlab 02
# TaskFlow: just pass the return value
n = count_rows(); load(n)

# classic operators: pull by task_id (Jinja or Python)
bash_command="echo rows={{ ti.xcom_pull(task_ids='count_rows') }}"
def fn(ti, **_): n = ti.xcom_pull(task_ids="count_rows")

Gotcha. Default size limit is tiny (tens of KB). XCom is for an id, a count, a path, a snapshot_id — the address of data, not data.

13

Variable

airflow.sdk

Key/value config in the metadata DB, editable in the UI. Environment names, bucket names, feature flags.

pythontwo ways
from airflow.sdk import Variable
bucket = Variable.get("lab_bucket")                    # inside a task — fine
bash_command="aws s3 ls s3://{{ var.value.lab_bucket }}/"   # Jinja — resolved at run time

Gotcha. Variable.get() at the top level of a DAG file runs on every parse (every ~30 s, for every DAG) and hammers the DB. Use it inside tasks or via Jinja. On MWAA, Variables can also come from Secrets Manager.

14

Connection · aws_conn_id

UI → Admin → Connections

Credentials and endpoints by id. Every AWS operator takes aws_conn_id, default "aws_default".

pythonlab 04 (emr mode)
EmrServerlessStartJobOperator(..., aws_conn_id="aws_default")   # default; can be omitted

# local lab: an env var is the quickest way to define one
AIRFLOW_CONN_AWS_DEFAULT='{"conn_type":"aws","extra":{"region_name":"us-east-1"}}'

Gotcha. On MWAA leave aws_default with no keys at all — the environment's execution role is used automatically. Keys in a Connection is the wrong pattern in AWS.

D · Wait

Sensors

A sensor is a task that polls. The three parameters that matter are the same on every one: poke_interval, timeout, and how it waits.

15

S3KeySensor

providers.amazon.aws.sensors.s3

Wait for an object (or a wildcard) to exist. The start of almost every AWS data pipeline.

pythonlab 03 (emr mode)
from airflow.providers.amazon.aws.sensors.s3 import S3KeySensor

wait = S3KeySensor(
    task_id="wait_raw",
    bucket_name="lab-bucket",
    bucket_key="raw/{{ ds }}/_SUCCESS",          # wait for the marker, not the data files
    wildcard_match=False,
    poke_interval=60, timeout=6 * 3600,
    deferrable=True,
)

Gotcha. Waiting for *.parquet succeeds on the first file while the writer is still producing the rest. Wait for a _SUCCESS marker or a manifest.

16

FileSensor · ExternalTaskSensor

providers.standard.sensors.filesystem / .external_task

Local-filesystem wait (the lab's stand-in for S3), and "wait for that task in that other DAG, same logical date".

pythonlab 03
from airflow.providers.standard.sensors.filesystem import FileSensor
from airflow.providers.standard.sensors.external_task import ExternalTaskSensor

FileSensor(task_id="wait", filepath="/opt/airflow/landing/{{ ds }}/orders.csv", poke_interval=10, timeout=600, mode="reschedule")
ExternalTaskSensor(task_id="wait_silver", external_dag_id="silver_pipeline", external_task_id="done", mode="reschedule")

Gotcha. ExternalTaskSensor matches on the same logical date by default. If the two DAGs have different schedules it waits forever unless you give it execution_delta or execution_date_fn. Assets (block 22) are usually the better tool now.

17

mode="reschedule" vs deferrable=True

parameters on every sensor and many operators

How the wait is paid for. poke holds a worker slot the whole time. reschedule releases it between checks. deferrable moves the wait to the triggerer entirely.

pythonrule of thumb
mode="poke"          # < 1 minute expected wait, fine
mode="reschedule"    # minutes to hours: task goes to up_for_reschedule between pokes
deferrable=True      # hours: async trigger in the triggerer; also on EMR/Glue/Athena operators

Gotcha. Twenty sensors in poke mode on a 16-slot worker pool = the whole environment appears hung. This is the #1 MWAA "my tasks are queued" ticket.

E · Call AWS

The amazon provider — the operators for this course

Every one of these follows the same shape: parameters that mirror the AWS API call, wait_for_completion, and deferrable. If you know the boto3 call, you know the operator.

18

EmrServerlessStartJobOperator

providers.amazon.aws.operators.emr

Submit a Spark job to an EMR Serverless application and wait for it. The one that runs your Iceberg scripts.

pythonlab 04 (emr mode) — full form in atlas 8 §05
from airflow.providers.amazon.aws.operators.emr import EmrServerlessStartJobOperator

EmrServerlessStartJobOperator(
    task_id="silver_02",
    application_id="{{ var.value.emr_app_id }}",
    execution_role_arn="{{ var.value.emr_role }}",
    job_driver={"sparkSubmit": {"entryPoint": "s3://b/labs/02_commits_time_travel.py",
                               "sparkSubmitParameters": "--conf spark.executor.memory=4g"}},
    configuration_overrides={"monitoringConfiguration": {"s3MonitoringConfiguration": {"logUri": "s3://b/logs/"}}},
    wait_for_completion=True, deferrable=True,
)

Gotcha. The job's own exit code decides success. A PySpark script that catches every exception and exits 0 will show green in Airflow while having done nothing. Let it raise.

19

EmrAddStepsOperator + EmrStepSensor

providers.amazon.aws.operators.emr / .sensors.emr

The EMR-on-EC2 equivalent: add a step to a running cluster, then wait for that step. Two tasks because the add call returns immediately.

pythonEMR on EC2
from airflow.providers.amazon.aws.operators.emr import EmrAddStepsOperator
from airflow.providers.amazon.aws.sensors.emr import EmrStepSensor

add = EmrAddStepsOperator(
    task_id="add_step", job_flow_id="{{ var.value.emr_cluster_id }}",
    steps=[{"Name": "silver", "ActionOnFailure": "CONTINUE",
            "HadoopJarStep": {"Jar": "command-runner.jar",
                              "Args": ["spark-submit", "--deploy-mode", "cluster", "s3://b/labs/01_anatomy.py"]}}])
wait = EmrStepSensor(task_id="wait_step", job_flow_id="{{ var.value.emr_cluster_id }}",
                     step_id="{{ ti.xcom_pull(task_ids='add_step')[0] }}", deferrable=True)
add >> wait

Gotcha. Steps on one cluster run serially by default. Ten Airflow tasks adding steps to the same cluster in parallel still execute one at a time on EMR — the parallelism you see in the grid is fake. Set StepConcurrencyLevel on the cluster or use EMR Serverless.

20

GlueJobOperator

providers.amazon.aws.operators.glue

Start a Glue job run and wait. Same shape as EMR Serverless; the script location and DPU settings live on the Glue job, not the operator.

pythonGlue 5.0
from airflow.providers.amazon.aws.operators.glue import GlueJobOperator

GlueJobOperator(task_id="glue_silver", job_name="silver_iceberg",
                script_args={"--run_date": "{{ ds }}"},
                wait_for_completion=True, deferrable=True)

Gotcha. If the Glue job's own timeout (default 480 min on 5.0) is longer than the task's execution_timeout, Airflow gives up and marks failed while Glue keeps running and billing. Align the two.

21

AthenaOperator · RedshiftDataOperator

providers.amazon.aws.operators.athena / .redshift_data

Run SQL and wait. Athena for validation queries over Iceberg; Redshift Data API for the serving layer (no JDBC connection to manage).

pythonthe verify-and-refresh tail of lab 04 in production
from airflow.providers.amazon.aws.operators.athena import AthenaOperator
from airflow.providers.amazon.aws.operators.redshift_data import RedshiftDataOperator

verify = AthenaOperator(task_id="verify_snapshot", database="lake", workgroup="primary",
    query="SELECT count(*) FROM \"silver_ledger$snapshots\" WHERE committed_at >= timestamp '{{ ds }} 00:00:00'",
    output_location="s3://b/athena-results/")
refresh = RedshiftDataOperator(task_id="refresh_mv", workgroup_name="serving", database="dev",
    sql="REFRESH MATERIALIZED VIEW mv_daily_summary", wait_for_completion=True)

Gotcha. AthenaOperator succeeds if the query succeeds — a count of zero is still success. To fail on a bad result, follow it with a @task that reads the result via AthenaHook.get_query_results and raises.

22

LambdaInvokeFunctionOperator · SnsPublishOperator · S3 operators

providers.amazon.aws.operators.lambda_function / .sns / .s3

The glue tasks: call a function, send a notification, move or write a small object.

python
from airflow.providers.amazon.aws.operators.lambda_function import LambdaInvokeFunctionOperator
from airflow.providers.amazon.aws.operators.sns import SnsPublishOperator
from airflow.providers.amazon.aws.operators.s3 import S3CopyObjectOperator, S3CreateObjectOperator

LambdaInvokeFunctionOperator(task_id="enrich", function_name="fx-rates", payload='{"date": "{{ ds }}"}')
SnsPublishOperator(task_id="notify", target_arn="arn:aws:sns:…:pipeline-alerts", message="nightly {{ ds }} done")
S3CreateObjectOperator(task_id="marker", s3_bucket="b", s3_key="gold/{{ ds }}/_SUCCESS", data="")

Gotcha. S3CopyObjectOperator is a single-object API call — it is not a way to move a partition. Data movement is a Spark job or an S3 Batch Operation; Airflow writes markers.

F · Steer

Control flow

23

@task.branch

airflow.sdk

Return the task_id (or list) to follow. Every other direct child is skipped.

pythonlab 02
@task.branch
def route(rows: int) -> str:
    return "full_rebuild" if rows > 10_000_000 else "incremental_merge"

route(count()) >> [full_rebuild, incremental_merge] >> join   # join needs none_failed_min_one_success

Gotcha. Inside a TaskGroup the id to return is the full one: "silver.full_rebuild".

24

ShortCircuitOperator

providers.standard.operators.python

If the callable returns falsy, everything downstream is skipped — cleanly, as SKIPPED, not FAILED. "Nothing landed today."

pythonlab 08
from airflow.providers.standard.operators.python import ShortCircuitOperator

gate = ShortCircuitOperator(task_id="anything_to_do", python_callable=lambda: files_landed() > 0,
                            ignore_downstream_trigger_rules=False)   # respect all_done on the cleanup task

Gotcha. By default it skips everything downstream, ignoring trigger rules. Set ignore_downstream_trigger_rules=False if a cleanup task with all_done must still run.

25

Dynamic task mapping — expand() / partial()

on any @task or operator

One definition, N instances, decided at run time. One per partition, file, table, region.

pythonlab 05
days = list_partitions()                                        # returns ["2026-08-28", ...]
done = process.partial(target="s3://b/silver").expand(day=days)   # N mapped instances
summarise(done)                                                 # receives the list of all results

# classic operators map too:
EmrServerlessStartJobOperator.partial(task_id="per_region", application_id=app, execution_role_arn=role)
                             .expand(job_driver=[driver(r) for r in regions])

Gotcha. Bound the fan-out: max_active_tis_per_dag= on the task, and never map over rows. A 10,000-way map is a scheduler problem, not a Spark problem.

26

TriggerDagRunOperator

providers.standard.operators.trigger_dagrun

Start another DAG by id, optionally passing conf and waiting for it.

pythonlab 07
from airflow.providers.standard.operators.trigger_dagrun import TriggerDagRunOperator

TriggerDagRunOperator(task_id="kick_gold", trigger_dag_id="gold_pipeline",
                      conf={"snapshot_id": "{{ ti.xcom_pull(task_ids='silver') }}"},
                      wait_for_completion=False)

Gotcha. Explicit and imperative — the producer must know the consumer's name. Assets (next) invert that: the consumer subscribes. Prefer Assets across team boundaries.

G · Time

Templates, Assets, backfill

27

Jinja templates — the eight you use

any templated field: bash_command, sql, bucket_key, …
jinjalab 01
{{ ds }}                    # 2026-09-02        logical date, the workhorse
{{ ds_nodash }}             # 20260902
{{ data_interval_start }}   # 2026-09-02T00:00:00+00:00 — use in WHERE clauses
{{ data_interval_end }}     # 2026-09-03T00:00:00+00:00 — exclusive upper bound
{{ logical_date }}          # datetime object; .strftime works
{{ run_id }}                # scheduled__2026-09-02T00:00:00+00:00 — put it in job names
{{ macros.ds_add(ds, -1) }} # yesterday
{{ var.value.bucket }}  {{ conn.aws_default.extra_dejson.region_name }}  {{ params.mode }}

Gotcha. Only fields listed in an operator's template_fields are rendered. A {{ ds }} inside a dict that is not templated stays literal — and your S3 key ends up containing the characters {{ ds }}. Check "Rendered Template" on the task instance.

28

Asset — outlets and schedule=[...]

airflow.sdk

Data-aware scheduling. A producer declares what it updated; a consumer runs when that happens. Called Dataset in Airflow 2.

pythonlab 07
from airflow.sdk import Asset
silver = Asset(name="silver_orders", uri="s3://b/silver/orders")

@task(outlets=[silver])                # producer, in DAG A
def write_silver(): ...

@dag(schedule=[silver], ...)          # consumer, DAG B: no cron
def gold(): ...

Gotcha. The Asset updates when the task succeeds, whether or not it actually wrote anything. It is a declaration, not a detection. Airflow does not watch S3 for you — that is what the sensor is for.

29

Backfill

CLI / UI

Create runs for a past date range. Only safe when tasks are idempotent by interval — which the templates above make natural.

bashlab 06
airflow backfill create --dag-id 06_backfill_and_catchup --from-date 2026-08-20 --to-date 2026-08-25
airflow backfill list
# Airflow 2 was: airflow dags backfill -s ... -e ...   (gone)

Gotcha. A backfill of a DAG whose tasks append rather than overwrite doubles the data. The Iceberg answer is overwritePartitions() / MERGE keyed on the interval — the same discipline the iceberg_deep labs taught.

H · Survive

Reliability

30

retries · execution_timeout · callbacks · pools

parameters

The four knobs that turn a demo into something an on-call engineer can trust.

pythonlab 04, 08
@task(
    retries=3, retry_delay=timedelta(minutes=1), retry_exponential_backoff=True, max_retry_delay=timedelta(minutes=15),
    execution_timeout=timedelta(hours=2),       # killed and marked failed after this; never hangs forever
    on_failure_callback=page_on_call,           # fn(context) — Slack, SNS, PagerDuty
    on_retry_callback=log_retry,
    pool="emr_serverless",                      # Admin → Pools: slot count = max concurrent jobs
    priority_weight=10,                         #  higher runs first when the pool is contended
)
def silver(): ...

Gotcha. retries re-runs the task from scratch. A Spark job that half-wrote a Parquet directory before dying leaves garbage a retry will read. With Iceberg it does not matter — the failed commit never became a snapshot. That is the cleanest argument for Iceberg under Airflow.
