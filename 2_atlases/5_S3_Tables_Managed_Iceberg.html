01 · The proposition

Iceberg, minus the cron jobs

A self-managed Iceberg table on S3 works fine until you have a thousand of them. Then somebody has to schedule compaction, expire snapshots, and hunt orphan files — forever, per table. S3 Tables is a bucket type that does all three continuously, on its own, and exposes the table through the Iceberg REST Catalog API so any engine can read it.

02 · Architecture

Two doors into the same table

Every engine reaches an S3 Table one of two ways: through the Glue Data Catalog integration (which is what makes it appear in Athena, Redshift and QuickSight), or directly through the Iceberg REST Catalog endpoint (which is how Spark, Flink and Trino connect). Same table, same files, two front doors.

TIP
Once Catalogue and Database are set in the Athena editor, use bare table names — orders, not the three-part quoted form. That is exactly what the AWS walkthrough does, and it removes an entire class of quoting errors.
03 · What you can store

Three kinds of table

Standard

Iceberg tables

The normal case. Full Iceberg semantics: ACID commits, schema and partition evolution, time travel, row-level updates.

Compaction supports Parquet, Avro and ORC file types.

Iceberg V3 ATHENA CANNOT READ

Variant, deletion vectors, row lineage

V3 adds the variant type (dynamic JSON shredded into typed Parquet columns), deletion vectors and row lineage.

Athena/Trino support for V3 is "No" in the AWS matrix — not just variant, the whole spec. Upgrade a table to V3 and your Athena users lose it.

System

Metadata tables

Six of them: $snapshots, $files, $history, $manifests, $partitions, $refs. Chapter 07.

These are standard Iceberg metadata tables surfaced by the engine — not something S3 Tables generates.

All three rows above are the same physical thing: an Iceberg table in a managed bucket. "Variant" is a column type rather than a table type, and the metadata tables are views over the Iceberg metadata tree rather than stored data. Deletion vectors also need opting in — they require format-version=3 plus write.delete.mode/write.update.mode/write.merge.mode set to merge-on-read.

04 · The headline feature

Three maintenance jobs, and their real defaults

This is the part worth memorising, because these numbers decide your storage bill and how far back you can time travel. Two jobs are configured per table; one is configured per bucket and applies to every table in it. All are on by default.

The four compaction strategies

strategywhat it doeswhen S3 picks it / when to pick it
auto DEFAULTS3 chooses for you based on the table's sort orderApplies sort if the table has a sort order in its metadata; binpack if it does not.
binpackCombines small files into larger ones, typically targeting sizes over 100 MB, applying pending deletesThe default for unsorted tables. Cheapest.
sortHierarchical sort on the columns in sort_order during compactionWhen queries frequently filter on specific columns. Requires a sort order in table properties.
z-orderBlends multiple attributes into one scalar for sorting, so several dimensions prune at onceWhen you filter across multiple dimensions simultaneously. Requires a sort order.
COST
AWS states plainly that compaction incurs additional cost, and z-order and sort may cost more than binpack. Setting sort or z-order also requires the s3tables:GetTableData permission, because the job must read your data to order it.

4TH
There is a fourth, opt-in maintenance operation the marketing rarely mentions: record expiration, configured per table via PutTableRecordExpirationConfiguration. It expires rows by age, not files — useful for retention policies you would otherwise implement as a scheduled DELETE.
TIER
If you put a table on S3 Intelligent-Tiering, note that compaction runs only on files in the Frequent Access tier. Delete files sitting on cold data are not reconciled, and files under 128 KB never tier at all. Also: Intelligent-Tiering is not automatic — tables are created in S3 Standard and the storage class cannot be changed after creation. You must specify it at CreateTable.
AWS CLI · tune the maintenancethe only way to change these
# compaction target file size -> 256 MB (valid range 64-512)
aws s3tables put-table-maintenance-configuration \
   --table-bucket-arn arn:aws:s3tables:us-east-1:111122223333:bucket/my-bucket \
   --type icebergCompaction --namespace mynamespace --name mytable \
   --value='{"status":"enabled","settings":{"icebergCompaction":{"targetFileSizeMB":256}}}'

# compaction strategy -> sort  (needs a sort_order + GetTableData permission)
aws s3tables put-table-maintenance-configuration \
   --table-bucket-arn arn:aws:s3tables:us-east-1:111122223333:bucket/my-bucket \
   --type icebergCompaction --namespace mynamespace --name mytable \
   --value='{"status":"enabled","settings":{"icebergCompaction":{"strategy":"sort"}}}'

# keep 10 snapshots and ~104 days of history instead of 1 and 5 days
aws s3tables put-table-maintenance-configuration \
   --table-bucket-arn arn:aws:s3tables:us-east-1:111122223333:bucket/my-bucket \
   --namespace my_namespace --name my_table \
   --type icebergSnapshotManagement \
   --value '{"status":"enabled","settings":{"icebergSnapshotManagement":{
             "minSnapshotsToKeep":10,"maxSnapshotAgeHours":2500}}}'

# orphan cleanup — BUCKET level, hits every table in the bucket
aws s3tables put-table-bucket-maintenance-configuration \
   --table-bucket-arn arn:aws:s3tables:us-east-1:111122223333:bucket/my-bucket \
   --type icebergUnreferencedFileRemoval \
   --value '{"status":"enabled","settings":{"icebergUnreferencedFileRemoval":{
             "unreferencedDays":4,"nonCurrentDays":10}}}'
05 · The trap

Two ways to silently switch off snapshot expiry

This is the single most important operational warning in the S3 Tables documentation, and it is easy to trigger by accident while doing something that looks like best practice. If either condition below is true, snapshot management fails for the entire table — no snapshots expire, and storage grows without limit.

SILENT
Nothing in Athena or Spark tells you this happened. The only signal is GetTableMaintenanceJobStatus returning FAILED. If you run S3 Tables in production, alarm on that API — it is the difference between a managed table and an unbounded storage bill.
06 · DDL that actually works

Athena and Spark, side by side

These two dialects are not interchangeable, and mixing them is the most common source of "mismatched input" errors. The rule: Athena quotes with " and needs table_type; Spark quotes with ` and needs USING iceberg.

Athena — CREATE TABLE

Three rules

  • TBLPROPERTIES ('table_type'='iceberg') is required
  • No LOCATION — storage is managed
  • No USING iceberg — that is Spark
Athena — CTAS

Three omissions

  • Omit location — managed
  • Omit table_type — already defaults to ICEBERG
  • Omit format — already defaults to PARQUET
  • Never pass is_external — not an S3 Tables property
Athena SQLset Catalogue + Database in the editor, then use bare names
-- namespace. Unqualified, with the Catalogue dropdown set.
CREATE DATABASE ecom_namespace;

-- hidden partitioning + bucketing, declared in the Iceberg schema
CREATE TABLE orders (
    order_id        string,
    user_id         string,
    order_timestamp timestamp,
    total_amount    double,
    country         string)
PARTITIONED BY (day(order_timestamp), bucket(128, user_id))
TBLPROPERTIES ('table_type' = 'iceberg');

-- CTAS: the WITH clause is usually just partitioning
CREATE TABLE high_value_orders
WITH (partitioning = ARRAY['day(order_timestamp)', 'bucket(64, user_id)'])
AS SELECT order_id, user_id, order_timestamp, total_amount
   FROM orders WHERE total_amount > 500.00;

-- full ACID DML
UPDATE orders SET country = 'USA' WHERE country = 'US';
DELETE FROM orders WHERE total_amount < 1;
MERGE INTO orders t USING staging s ON t.order_id = s.order_id
  WHEN MATCHED THEN UPDATE SET total_amount = s.total_amount
  WHEN NOT MATCHED THEN INSERT *;

-- time travel
SELECT * FROM orders FOR TIMESTAMP AS OF (current_timestamp - INTERVAL '1' HOUR);
SELECT * FROM orders FOR VERSION AS OF 8333017788700497002;
Spark SQL — EMR / Gluebackticks, USING iceberg, dotted metadata tables
-- note the backticks and USING iceberg — both WRONG in Athena
CREATE TABLE `my_catalog`.`ecom_namespace`.`orders` (
    order_id        STRING,
    user_id         STRING,
    order_timestamp TIMESTAMP,
    total_amount    DOUBLE,
    country         STRING)
USING iceberg
PARTITIONED BY (days(order_timestamp), bucket(128, user_id));

-- things ONLY Spark can do on an S3 Table:
ALTER TABLE ... RENAME COLUMN country TO country_code;
ALTER TABLE ... ADD PARTITION FIELD hours(order_timestamp);
ALTER TABLE ... WRITE ORDERED BY country_code ASC;   -- unlocks sort/z-order compaction

-- metadata tables use a DOT in Spark, a $ in Athena
SELECT * FROM `my_catalog`.`ecom_namespace`.`orders`.snapshots;
WHY
The dialect difference is not cosmetic. Athena is Trino-derived; EMR/Glue run Spark SQL. A SageMaker Unified Studio editor can be wired to either, which is why the same file can produce two completely different parser errors in two tabs. Read the "expecting" list in the error: if it mentions BACKQUOTED_IDENTIFIER, CODEGEN or MSCK, you are on Spark.
07 · Metadata tables

The table's own telemetry, as SQL

Everything the maintenance jobs act on is visible to you first. These queries cost almost nothing — they read metadata, not data — and they are how you audit whether the managed maintenance is actually keeping up.

metadata tableanswersthe field that matters
$snapshotsWhat each commit did, and whenoperation, summary['added-records'], committed_at
$filesCurrent data files and their statisticsfile_size_in_bytes — compare against the 512 MB compaction target
$historyWhen each snapshot became current, and its lineageparent_id + is_current_ancestor — two sharing a parent with one false means a rollback happened
$manifestsThe pruning layer's own healthadded_data_files_count, partition_summaries
$partitionsPer-partition file counts and delete debtfile_count, spec_id (two spec_ids = a partition evolution happened)
$refsBranches and tagstype — any row here that you created disables snapshot expiry (ch 05)
Athena · the three queries worth schedulingmetadata only — near-zero cost
-- 1. Is compaction keeping up? Average file size should trend toward 512 MB.
SELECT partition,
       count(*)                                AS files,
       cast(avg(file_size_in_bytes) AS bigint) AS avg_bytes
FROM "orders$files"
GROUP BY partition ORDER BY files DESC;

-- 2. How far back can I actually time travel? (bounded by maxSnapshotAgeHours)
SELECT min(committed_at) AS oldest_reachable,
       max(committed_at) AS newest,
       count(*)          AS snapshots
FROM "orders$snapshots";

-- 3. Am I about to disable my own snapshot expiry? Anything here but 'main' is a risk.
SELECT name, type, snapshot_id FROM "orders$refs";

Query 3 is the one to put on a schedule. It is the cheap early warning for the chapter 05 trap: if a branch or tag shows up that nobody intended to keep, snapshot expiry has already stopped for that table.

08 · Limitations

What Athena will refuse

AWS publishes these under "Considerations and limitations" and they are the difference between a demo that works and one that dies in front of an audience.

Not supported on S3 Tables via Athena

Three DDL statements

  • ALTER TABLE … RENAME
  • CREATE VIEW
  • ALTER DATABASE

Column renames and partition evolution must come from Spark. Views must live in the regular awsdatacatalog, or be materialised as a table.

Blocked by workgroup configuration

Writes can be disabled

  • Workgroups with SSE-KMS / CSE-KMS encryption: no INSERT, UPDATE, DELETE or MERGE on S3 Tables
  • Workgroups with S3 Requester Pays: no DML at all

If your writes fail and the SQL is right, check the workgroup before the SQL.

OPTIMIZE / VACUUM

Managed, not yours

Listed as exceptions: compaction and snapshot management happen in S3. Running them manually is not the intended path — configure the maintenance jobs instead (ch 04).

Failed CTAS

DROP TABLE will not clean up

AWS: "you cannot use the Athena DROP TABLE statements to remove the table that was partially created by the query." Use aws s3tables delete-table.

EMR above 7.5

DROP TABLE is not supported at all

Verbatim: "Amazon EMR versions higher than 7.5: DROP TABLE is not supported. You can use the S3 Tables DeleteTable REST API to delete a table." On exactly 7.5, also set …cache-enabled=false.

Over the S3 Tables REST endpoint

No CTAS, no nested namespaces

stage-create is unsupported, so CTAS returns 400 when you connect Spark straight to s3tables.<region>.amazonaws.com/iceberg. Multilevel namespaces are unsupported. A metadata.json over 50 MB fails outright.

CTAS does work in Athena via the Glue path — don't let the two blur.

Quotas and the naming rule that silently hides your table

Default quotas — adjustable via Support

Smaller than people assume

  • 10 table buckets per Region per account
  • 10,000 namespaces per table bucket
  • 10,000 tables per table bucket

Table buckets are not in a global namespace — a name only has to be unique within your Region.

The inverse naming rules

Hyphens and underscores swap

  • Table buckets: lowercase, numbers, hyphens — no underscores, no periods, 3–63 chars
  • Tables & namespaces: lowercase, numbers, underscores — no hyphens, no periods, 1–255 chars

Capital letters break everything. AWS: a table whose name or definition contains capitals "isn't supported by AWS Lake Formation or the AWS Glue Data Catalog… your table won't be visible to AWS analytics services such as Amazon Athena", failing with Unsupported Federation Resource - Invalid table or column names.

AWS CLI · recovering from a failed CTASthe documented path
# TABLE_ALREADY_EXISTS after a failed CTAS? DROP TABLE cannot fix it.
aws s3tables delete-table \
  --table-bucket-arn arn:aws:s3tables:us-east-1:<ACCOUNT>:bucket/<TABLE_BUCKET> \
  --namespace <NAMESPACE> --name <TABLE> --region us-east-1

# confirm it is gone
aws s3tables list-tables \
  --table-bucket-arn arn:aws:s3tables:us-east-1:<ACCOUNT>:bucket/<TABLE_BUCKET> \
  --namespace <NAMESPACE> --region us-east-1

# every value you need is inside the Athena error text:
#   "catalog:<ACCOUNT>:s3tablescatalog/<TABLE_BUCKET>$schema:<NAMESPACE>"
09 · Views

Where a view can and cannot live

The distinction people miss: a virtual view is a stored SQL string with no data, while a materialized view is a real table holding precomputed rows. Only one of them is free to refresh, and neither can be created directly on an S3 Table from Athena.

SPLIT
"Athena supports materialized views" is true and false at the same time, which is why people get it wrong live. Glue Data Catalog materialized views are created with Apache Spark 3.5.6+ running in EMR, Glue, or Athena's Spark engine (notebooks). Athena SQL — the Trino engine you type into — cannot: CREATE MATERIALIZED VIEW, REFRESH, ALTER, DROP, INSERT, UPDATE, MERGE, DELETE, OPTIMIZE and VACUUM are all unsupported there. It can SELECT, DESCRIBE, SHOW TABLES and join them.
Spark SQL — the real materialized viewEMR / Glue / Athena notebooks, Spark 3.5.6+
-- a managed table holding precomputed results, in Iceberg format
CREATE MATERIALIZED VIEW sales_summary
SCHEDULE REFRESH EVERY 1 HOUR              -- minimum interval is one hour
AS SELECT country, count(*) AS orders, sum(total_amount) AS revenue
   FROM orders GROUP BY country;

REFRESH MATERIALIZED VIEW sales_summary;                -- manual refresh
ALTER MATERIALIZED VIEW sales_summary ADD SCHEDULE REFRESH EVERY 2 HOURS;
DESCRIBE MATERIALIZED VIEW sales_summary;
AWS CLIrefresh an MV whose base tables live in a table bucket
aws glue start-materialized-view-refresh-task-run \
  --catalog-id <ACCOUNT_ID>:s3tablescatalog/<TABLE_BUCKET> \
  --database-name <NAMESPACE> --table-name sales_summary

One constraint that decides the design: a materialized view can only reference Iceberg tables registered in the Glue Data Catalog as base tables, and the minimum automatic refresh interval is one hour. For anything fresher, materialise with CTAS and refresh it yourself on your own cadence — the pattern shown below.

Athenathe supported stand-in, with an idempotent refresh
-- materialise instead of CREATE VIEW
CREATE TABLE mv_hourly_metrics
WITH (partitioning = ARRAY['day(order_hour)'])
AS SELECT date_trunc('hour', order_timestamp) AS order_hour,
          country, count(*) AS orders, sum(total_amount) AS revenue
   FROM orders GROUP BY 1, 2;

-- "refresh" = replace only the affected window. Rerun it five times,
-- get the same table. That idempotence is what lets you schedule it.
DELETE FROM mv_hourly_metrics WHERE order_hour >= TIMESTAMP '2026-09-01 00:00:00';

INSERT INTO mv_hourly_metrics
SELECT date_trunc('hour', order_timestamp), country, count(*), sum(total_amount)
FROM orders WHERE order_timestamp >= TIMESTAMP '2026-09-01 00:00:00'
GROUP BY 1, 2;
10 · Verification log

What was checked, and what was corrected

Every claim on this page was checked against AWS documentation. Several things widely repeated about S3 Tables did not survive that check — those are listed here so you can correct them if you have repeated them too.

ClaimStatusWhat the docs actually say
Compaction default target 512 MB, range 64–512 MBVERIFIEDStated directly, with the targetFileSizeMB CLI example.
Four compaction strategies: auto, binpack, sort, z-orderVERIFIEDauto picks sort when a sort order exists, binpack otherwise.
Snapshot defaults: 1 snapshot, 120 hoursVERIFIEDMinimumSnapshots 1, MaximumSnapshotAge 120 h.
Unreferenced file removal 3 / 10 daysVERIFIEDunreferencedDays 3, nonCurrentDays 10 — and it is bucket-level, not table-level.
Branches/tags break snapshot expiryVERIFIED"snapshot management will fail for the entire table" — the most under-known fact about S3 Tables.
CREATE VIEW works on S3 Tables in AthenaFALSEExplicitly listed as not supported, alongside ALTER TABLE RENAME and ALTER DATABASE.
CTAS needs table_type and formatFALSEBoth already default. Passing is_external misdirects the write entirely.
"Automatic S3 Intelligent-Tiering cuts storage cost up to 80%"WRONG TWICEIt is not automatic: "all tables are created in the S3 Standard storage class and cannot be moved to S3 Intelligent-Tiering" — you must opt in at CreateTable, and the class is immutable afterwards. And no 80% figure exists in the docs at all.
"10× higher TPS and 3× faster queries"MARKETINGNot in the documentation. The docs-safe sentence is unquantified: table buckets "provide higher transactions per second (TPS) and better query throughput compared to self-managed tables in S3 general purpose buckets."
Compaction also applies row-level deletesVERIFIED"When combining objects, compaction also applies the effects of row-level deletes in your table." This is what reconciles merge-on-read debt for you.
Athena can read Iceberg V3 tablesFALSEThe AWS V3 support matrix lists Athena (Trino): No for both V3 and variant. Upgrading is one-way and removes the table from Athena.
Athena can create materialized viewsFALSEAthena SQL cannot CREATE, REFRESH, ALTER or DROP them — only SELECT. Creation requires Spark 3.5.6+ in EMR, Glue, or Athena notebooks.
Athena CTAS on S3 Tables is unsupportedSPLITSupported in Athena. Unsupported over the S3 Tables REST endpoint, where stage-create returns 400. Two different access paths, opposite answers.
Lake Formation is required for the Glue integrationNO LONGERIAM-based access is the default path in 32 Regions; Lake Formation is optional there and still required elsewhere.
Metadata tables are generated by S3 TablesRE-FRAMEDThey are standard Iceberg metadata tables surfaced by the query engine. Not to be confused with S3 Metadata, a separate feature that materialises inventory tables.
Minimum engine versionsVERIFIEDEMR 7.5+ and Glue 5.0+. No Athena engine-version floor is documented — do not claim one.
REST
Two different REST endpoints exist and they are not interchangeable. The S3 Tables endpoint is https://s3tables.<region>.amazonaws.com/iceberg with signing name s3tables and the URL-encoded table bucket ARN as the path prefix. The Glue endpoint is https://glue.<region>.amazonaws.com/iceberg with signing name glue and warehouse <account>:s3tablescatalog/<bucket>. AWS recommends the Glue one for Spark and PyIceberg clients.
METHOD
The two rejected claims above are the reason this page exists in this form. When a number appears in a slide deck without a doc URL behind it, assume it is a launch-blog headline until proven otherwise — especially percentage improvements and multipliers.
