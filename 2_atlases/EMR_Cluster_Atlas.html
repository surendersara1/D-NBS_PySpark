01 · Anatomy

Every process, and which box it sits on

A node's role decides what it holds, and what it holds decides whether losing it is free or expensive. That single sentence is the whole spot-instance strategy: task nodes hold nothing durable, so put them on spot; core nodes hold shuffle files and HDFS, so don't.

03 · Spot interruption

AWS gives you two minutes. Here's what Spark does with them.

A spot reclaim is not a crash — it is an announced departure. EC2 posts an interruption notice roughly two minutes ahead, EMR sees it, and Spark can decommission the node gracefully instead of discovering the loss by timeout. The two scenarios below have wildly different costs.

spark-defaultsmake the two minutes count
# Use the interruption notice instead of discovering loss by timeout
spark.decommission.enabled                          true
spark.storage.decommission.enabled                  true
spark.storage.decommission.shuffleBlocks.enabled    true   # move shuffle off the dying node
spark.storage.decommission.rddBlocks.enabled        true   # move cached blocks too

# Tolerate more churn before giving up on a task or a stage
spark.task.maxFailures                              8      # default 4
spark.stage.maxConsecutiveAttempts                  8      # default 4

# Don't let one flaky node poison the run
spark.excludeOnFailure.enabled                      true
WIN
Shuffle-block migration turns scenario B into scenario A. With decommissioning enabled, Spark copies shuffle output off the doomed node during the notice window, so its departure no longer forces a stage recompute. On spot-heavy clusters this is the single highest-value setting on this page.
04 · The question everyone asks

Do we start from the beginning? Almost never.

Spark does not re-run your job. It re-runs the smallest set of partitions whose results were lost, using lineage — the recipe for recomputing any partition from its parents. Completed stages that still have their shuffle files intact are simply reused.

05 · Cache, checkpoint, and the long lineage

Three ways to not do the work twice

Lineage is free insurance, but it has a cost: a very long chain means a very long recompute. cache keeps results handy but stays recomputable; checkpoint writes to reliable storage and cuts the chain. They solve different problems and people constantly reach for the wrong one.

06 · Streaming restart

Resume from the checkpoint, not from the start

A Structured Streaming job that dies — spot reclaim, deploy, crash — restarts by reading its checkpoint directory: the offsets it had consumed and the state it had accumulated. It picks up exactly where it stopped, with no duplicates and no gap.

07 · Multi-tenancy

One cluster, many jobs — who gets the cores?

A long-running cluster is usually shared. Each submitted application gets its own driver and its own executors — they never share a JVM — and YARN arbitrates between them. Understanding the two levels of scheduling is how you stop one analyst's query from starving the nightly load.

spark-defaultssharing a cluster politely
# Give executors back when idle, grab more when the queue is deep
spark.dynamicAllocation.enabled            true
spark.dynamicAllocation.minExecutors       2
spark.dynamicAllocation.maxExecutors       40
spark.dynamicAllocation.executorIdleTimeout 60s
spark.shuffle.service.enabled              true   # REQUIRED: serves shuffle for removed executors

# Fair scheduling BETWEEN concurrent queries in one app (notebooks, Thrift)
spark.scheduler.mode                       FAIR

# Submit into a named YARN queue
spark.yarn.queue                           etl
TRAP
Dynamic allocation without the external shuffle service is a data-loss bug waiting to happen. When Spark removes an idle executor, whatever shuffle files it was serving go with it — unless the shuffle service on that node can keep serving them. Enable both or neither.

Job A — 12 min nightly

Don't build a cluster

EMR's 5–10 min spin-up is most of the runtime. Glue Flex or EMR Serverless wins on both cost and ops.

Job B — 6 h daily reprocess

This is spot's moment

Small on-demand core group for shuffle, large spot task fleet for compute. Roughly $25–40/run against ~$132 on Glue.

Job C — analyst asking questions

Not a cluster problem

Athena over the same tables. Spinning up Spark to answer SELECT … GROUP BY is the most common waste in a young platform.

BOARD
The four sentences to leave on the whiteboard: ① S3 is storage, the cluster is compute — kill it any night. ② Role decides risk: task nodes hold nothing, core nodes hold shuffle. ③ Spot loss re-runs tasks, not jobs — unless the driver or shuffle files went with it. ④ Streaming resumes from its checkpoint; batch relies on lineage, so make long batch jobs idempotent and stepwise.
