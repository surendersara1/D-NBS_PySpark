01 · Clear this up first

Three unrelated things are all called "partition"

Most partitioning confusion is vocabulary, not concept. Spark uses one word for three things that happen at different times, are controlled by different settings, and fail in different ways. Name which one you mean and half the questions answer themselves.

02 · Hash partitioning

Route by key — the default for everything

Compute hash(key) % numPartitions and send the row there. Every row with the same key lands in the same partition, on the same machine, guaranteed. This is what makes groupBy and join correct, and it is what Spark does automatically whenever you aggregate or join.

PySparkyou rarely call this explicitly — Spark does
# implicit: every one of these hash-partitions under the hood
df.groupBy("region").agg(F.sum("amount"))
df.join(other, "customer_id")
df.dropDuplicates(["order_id"])
Window.partitionBy("region")

# explicit: only when you will reuse the same partitioning repeatedly
df = df.repartition(200, "customer_id").cache()
df.join(a, "customer_id")   # no re-shuffle
df.join(b, "customer_id")   # no re-shuffle
Reach for it when

Grouping or joining

Any time all rows for a key must meet. Also before repeated joins on the same key — partition once, reuse.

It hurts when

One key dominates

60% of rows in one key = 60% of the shuffle on one reducer. Everything waits for it. Confirm AQE is on; then salt.

The knob

shuffle.partitions

200 by default. On 320 cores that leaves 120 idle chewing 1 GB tasks. Set 2–4× core count.

03 · Range partitioning

Route by value band — the one that enables sorting

Hash destroys order: adjacent values land in unrelated partitions. Range partitioning instead gives each partition a contiguous band of values, so partition 0's maximum is below partition 1's minimum. Sort each band locally and the concatenation is globally sorted — no machine ever held the whole dataset.

PySparkand the cheaper alternative
# explicit range partitioning — balanced, order-preserving
df.repartitionByRange(64, "order_amount")

# implicit: a global sort IS a range shuffle
df.orderBy("order_amount")          # sample pass + range shuffle + local sort

# the cheap version — sorted WITHIN each partition, no shuffle at all
df.sortWithinPartitions("order_amount")
COST
orderBy before a write is expensive vanity. If you are sorting so the output files "look tidy", you have paid a full range shuffle plus a sampling scan for cosmetics. Use sortWithinPartitions() if you want local clustering — or nothing at all.
04 · Round-robin

Deal the rows out like cards

No key, no hash, no order — just deal each row to the next partition in turn. The result is perfectly even sizes and zero locality. Use it when your problem is imbalance, not grouping.

PySparknote the missing column argument
df.repartition(400)              # round-robin — even, no key locality
df.repartition(400, "region")    # hash — locality, uneven sizes
05 · Coalesce

The one that moves nothing

Every other strategy is a shuffle. coalesce is not: it merges adjacent partitions in place, on the machines already holding them. That makes it nearly free — and gives it two hard limits. It can only shrink, and it can leave you badly unbalanced.

06 · Broadcast

The best shuffle is the one you delete

If one side of a join is small enough, don't partition either side — send the whole small table to every executor and join locally. The shuffle disappears entirely. This is the single largest win available on a typical star-schema join.

PySparkbe explicit when you know
from pyspark.sql.functions import broadcast
facts.join(broadcast(dims), "dim_id")

# AQE can convert a sort-merge join to a broadcast at RUNTIME once it sees
# the real size — but it cannot help if the estimate was wrong before the
# first stage ran. Be explicit when you already know the answer.
spark.conf.set("spark.sql.autoBroadcastJoinThreshold", "104857600")  # 100 MB
07 · Partitioning on write

The decision every future query lives with

Shuffle partitioning lasts one job. Storage partitioning lasts until someone rewrites the table. Pick the column your users actually filter on — usually date, then a low-cardinality dimension — and never pick something high-cardinality.

08 · Bucketing

Pre-shuffle once, join for free forever

Bucketing writes data already hash-partitioned on disk. Two tables bucketed the same way on the same key can be joined with no shuffle at all — the matching rows are already co-located. You pay the shuffle once at write time instead of on every query.

ORDER
Diagnose in this order before changing any partitioning: ① Am I reading too much? Check PartitionFilters. ② How many shuffles are there — can one be broadcast away? ③ Is it skewed — is max task time 40× the median? ④ Are there fewer tasks than cores? Only then reach for a partitioner.
