01The flaw Iceberg was built to fix

Hive tracked directories. Iceberg tracks files.

Every Hive limitation descends from one design decision: a table is defined as a set of directories. The Metastore can atomically swap a partition directory, so that is the smallest unit of change — you cannot atomically swap one file. Planning means LIST-ing prefixes in S3, which is slow, throttled, and gets worse with scale. Netflix's fix in 2017 was to define a table as a canonical list of files, written down in metadata. Everything else — ACID, time travel, evolution — falls out of that one change.

Consistency

All-or-nothing across partitions

An update spanning 40 partitions is one commit. Readers see the state before or after — never a half-applied write.

Performance

Planning stops being a scan

No file/directory listing. Manifests carry partition ranges and column bounds, so whole manifests and whole files are discarded before a byte of Parquet opens.

Evolvability

Layout is metadata, not physics

Partition scheme and schema change without rewriting history, because both are recorded per-snapshot rather than baked into directory names.

02Anatomy

Three layers, four hops, one pointer

An Iceberg table is a tree with the catalog at the root and Parquet at the leaves. Read it top-down to understand queries; bottom-up to understand writes. Each level exists to throw away work at the level below it — the manifest list prunes whole manifests, a manifest prunes whole data files, and only what survives is opened.

PySpark · inspect the real treeruns on EMR, Glue, or your laptop
# Which metadata.json does the catalog currently point at?
spark.sql("""
  SELECT * FROM glue_catalog.silver_db.orders.metadata_log_entries
  ORDER BY timestamp DESC LIMIT 1
""").show(truncate=False)

# Every data file the current snapshot references, with its statistics
spark.sql("""
  SELECT file_path, record_count, file_size_in_bytes, partition,
         lower_bounds, upper_bounds
  FROM glue_catalog.silver_db.orders.files
""").show(truncate=False)

# The manifests themselves — how many files each one tracks
spark.sql("""
  SELECT path, length, added_data_files_count,
         existing_data_files_count, deleted_data_files_count
  FROM glue_catalog.silver_db.orders.manifests
""").show(truncate=False)

Those three queries are the fastest way to make this diagram real in a classroom: run them against a table you just wrote and the tree above stops being an illustration. .files is the leaf level, .manifests is the level that prunes it, and .metadata_log_entries is the pointer the catalog hands out.

03The write path

Three commits, watched from the inside

Nothing teaches the format like following one table through CREATE, INSERT and MERGE and watching the tree grow. Each commit writes a new metadata file — v1, v2, v3 — appends a snapshot to the list, and moves the catalog pointer exactly once at the end. Old files are never edited.

Spark SQLthe three statements the diagram follows
-- ① CREATE: metadata only. No data files, no manifest, no manifest list.
CREATE TABLE glue_catalog.silver_db.orders (
    order_id     BIGINT,
    customer_id  BIGINT,
    order_amount DECIMAL(10,2),
    order_ts     TIMESTAMP)
USING iceberg
PARTITIONED BY (hours(order_ts));        -- hidden partitioning, ch 07

-- ② INSERT: one data file, one manifest, one manifest list, snapshot s1
INSERT INTO glue_catalog.silver_db.orders
VALUES (123, 456, 36.17, '2026-03-07 08:10:23');

-- ③ MERGE: upsert. Copy-on-write rewrites the touched file; snapshot s2
MERGE INTO glue_catalog.silver_db.orders o
USING (SELECT * FROM orders_staging) s
   ON o.order_id = s.order_id
WHEN MATCHED THEN UPDATE SET order_amount = s.order_amount
WHEN NOT MATCHED THEN INSERT *;
KEY
Notice what the engine reads before writing anything: the catalog, for two reasons — to learn the current schema so the write conforms to it, and to learn the partition spec so rows land in the right place. A write is never blind.
04The commit protocol

Optimistic concurrency and the atomic swap

Iceberg does not lock. Every writer assumes it will win, does all its expensive work speculatively, and gambles on a single compare-and-swap at the very end: "replace the pointer, but only if it still equals the version I started from." Exactly one writer can win that race. The loser is not corrupt and not lost — it re-reads, revalidates its work against the new state, and retries.

Why the crash case is safe

Data files first, pointer last

If the job dies after writing Parquet but before the swap, no reader ever saw those files — the table is exactly as it was. The cost is orphan files, cleaned by remove_orphan_files.

Where it can genuinely fail

Conflicting row-level changes

If B's MERGE touches files A just replaced, revalidation detects it and B must redo the row-level work, not just the metadata. Hot tables with many concurrent writers should partition writes so they touch disjoint files.

05The read path

A pruning cascade, not a scan

A query never asks "what files exist?" — it asks the metadata "which files can possibly contain rows matching this predicate?" and gets a short list. Each level throws away more work than the one below it, and the number of Parquet files actually opened is usually a rounding error against the table's size.

PySpark · prove the pruningrun this before blaming the cluster
df = (spark.read.table("glue_catalog.silver_db.orders")
           .filter("order_ts >= '2026-01-01' AND order_ts < '2026-02-01'"))

df.explain("formatted")
# Look for these two lines in the scan node:
#   PushedFilters:     [GreaterThanOrEqual(order_ts,…), LessThan(order_ts,…)]
#   number of partitions read / files: should be a small fraction of .files

# Compare against the whole table — that ratio IS your pruning
total = spark.sql("SELECT count(*) FROM glue_catalog.silver_db.orders.files")
total.show()   # every data file the current snapshot tracks

If PushedFilters comes back empty, the predicate never reached the metadata and Iceberg is reading everything — the single cheapest performance win available, and the first thing to check on a slow job.

06Time travel & rollback

The same tree, entered at a different door

Time travel needs no backup, no restore and no copy, because every past snapshot is still a complete, valid tree — it was never deleted, only superseded as "current". Reading last Tuesday is the ordinary read path with a different starting snapshot. Rollback is the same trick pointed forward: make an old snapshot current again.

TRAP
If you give TIMESTAMP AS OF a moment with no exact snapshot, Iceberg picks the newest snapshot older than it. Ask for a time before the table existed and you get IllegalArgumentException: Cannot find a snapshot older than … — not an empty result. And you can never travel to an expired snapshot.
07Hidden partitioning & evolution

The partition column that isn't there

Hive made you invent a month column, populate it, and then remember to filter on it — and anyone who filtered only the timestamp silently got a full table scan. Iceberg records the transform in metadata instead, so the natural query prunes. And because partitioning lives in metadata rather than in directory names, you can change it without rewriting a single file.

Spark SQL · evolving a live tablemetadata-only — no files move
-- start coarse
CREATE TABLE glue_catalog.silver_db.members (…)
USING iceberg PARTITIONED BY (years(registration_ts));

-- volume grew: go finer. Old data stays under years(), new data lands under months()
ALTER TABLE glue_catalog.silver_db.members ADD PARTITION FIELD months(registration_ts);

-- drop a field you no longer want to partition on (schema is untouched)
ALTER TABLE glue_catalog.silver_db.members DROP PARTITION FIELD bucket(24, id);

-- migrated a Hive table partitioned on a derived column? Re-express it as a transform:
ALTER TABLE glue_catalog.silver_db.members
  REPLACE PARTITION FIELD registration_day WITH days(registration_ts) AS day_of_registration;

-- and set a sort order so every writer clusters the data the same way
ALTER TABLE glue_catalog.silver_db.members WRITE ORDERED BY region ASC, registration_ts DESC;
SEE
Which spec produced which files? SELECT spec_id, COUNT(*) FROM …orders.partitions GROUP BY spec_id shows the split across specs — the fastest way to confirm an evolution actually took effect.
08Schema evolution

Columns have IDs, so renaming is free

In Hive, a column is a name in a position — rename it and old files no longer line up; drop a middle column and everything after it shifts. Iceberg assigns every column a permanent integer ID at creation and tracks last-column-id in the metadata so an ID is never reused. Every read resolves by ID, not by name or position, which makes add, rename, drop and reorder pure metadata operations.

Requires the SQL extensions

What needs IcebergSparkSessionExtensions

  • ADD/DROP/REPLACE PARTITION FIELD
  • WRITE ORDERED BY / WRITE DISTRIBUTED BY PARTITION
  • SET/DROP IDENTIFIER FIELDS
  • every CALL …system.* procedure
Works without them

Plain Spark SQL is enough for

  • RENAME TO, SET TBLPROPERTIES
  • ADD/RENAME/ALTER/DROP COLUMN
  • all DML: INSERT, MERGE, UPDATE, DELETE

Add the extensions anyway — you will want the procedures on day two.

09Row-level operations

Copy-on-write, merge-on-read, and the two kinds of delete

Data files are immutable, so "update 10 rows" always means writing something new. The only question is what you write: a fresh copy of every file those rows lived in (copy-on-write), or a small side-file recording what to ignore (merge-on-read). You are trading write latency against read latency, and the choice is per-operation.

Spark SQL · set it per operationall three default to copy-on-write
CREATE TABLE glue_catalog.silver_db.people (id int, first_name string, last_name string)
USING iceberg
TBLPROPERTIES (
  'write.delete.mode' = 'copy-on-write',   -- rare, big deletes → keep reads clean
  'write.update.mode' = 'merge-on-read',   -- frequent small updates → keep writes fast
  'write.merge.mode'  = 'merge-on-read'
);

-- change your mind later; it only affects future operations
ALTER TABLE glue_catalog.silver_db.people SET TBLPROPERTIES (
  'write.merge.mode' = 'copy-on-write'
);

-- how much delete-file debt am I carrying right now?
SELECT partition,
       position_delete_file_count,
       equality_delete_file_count,
       file_count
FROM glue_catalog.silver_db.people.partitions
ORDER BY equality_delete_file_count DESC;
MoR
Two operational rules before you turn merge-on-read on: every engine that reads the table must understand delete files (older readers will silently return deleted rows), and you must schedule compaction — rewrite_data_files is what reconciles deletes back into the data and stops read cost from growing forever.
10Compaction & layout

Fixed costs you must pay, variable costs you shouldn't

Reading the rows your query needs is a fixed cost. Opening, seeking and closing thousands of tiny files to get at them is a variable cost — pure overhead, and the one you can engineer away. Compaction rewrites many small files into few large ones; sorting and Z-ordering decide which rows land together so that pruning has something to bite on.

Spark SQL · the real compaction callnamed arguments, with a where filter
-- Hourly job for streaming ingest: binpack only the last hour, commit as it goes
CALL glue_catalog.system.rewrite_data_files(
  table    => 'silver_db.orders',
  strategy => 'binpack',
  where    => 'order_ts between "2026-09-01 09:00:00" and "2026-09-01 09:59:59"',
  options  => map(
    'target-file-size-bytes',   '1073741824',   -- 1 GB
    'max-file-group-size-bytes','10737418240',  -- 10 GB: split huge partitions
    'rewrite-job-order',       'bytes-asc',
    'partial-progress-enabled','true'          -- commit per file group; readers benefit early
  ));

-- Weekend job: globally re-sort the table so reads cluster
CALL glue_catalog.system.rewrite_data_files(
  table      => 'silver_db.orders',
  strategy   => 'sort',
  sort_order => 'region ASC NULLS LAST, order_ts DESC');

-- Multi-dimensional filters instead? z-order, passed as a sort_order
CALL glue_catalog.system.rewrite_data_files(
  table      => 'silver_db.orders',
  strategy   => 'sort',
  sort_order => 'zorder(customer_id, order_amount)');
where

Always scope the job

Without where, the whole table is a candidate. Scoping to one hour or one partition is the difference between a 3-minute job and a 6-hour one.

partial-progress-enabled

Commit as you go

Each finished file group becomes a snapshot, so long jobs deliver value early and survive OOM. Cost: more snapshots — cap with partial-progress-max-commits.

Interaction to remember

Compaction re-partitions

Rewritten files adopt the current partition spec. After a partition evolution, filter your compaction so it doesn't quietly restructure history.

11Maintenance & observability

Metadata tables are your monitoring system

Iceberg exposes its own internals as ordinary SQL tables, so "which partitions need compacting?" and "is this table accumulating delete debt?" are queries, not guesswork. Every maintenance procedure below should be driven by one of them — diagnose first, then run the procedure with a filter, never blanket maintenance on a schedule you never tuned.

.historyEvery time the current snapshot changed, and its lineageparent_id + is_current_ancestor — two snapshots sharing a parent where only one is a current ancestor means somebody rolled back
.snapshotsWhat each commit did and how much it addedoperation (append / overwrite / delete), summary['added-records']
.filesCurrent data files with full statisticscontent: 0=data, 1=position delete, 2=equality delete; plus file_size_in_bytes, null_value_counts

Spark SQL · the three diagnostics worth schedulingcheap — metadata only, no data scanned
-- ① Which partitions need compaction? Many files, small average size.
SELECT partition, COUNT(*) AS num_files, AVG(file_size_in_bytes) AS avg_size
FROM glue_catalog.silver_db.orders.files
GROUP BY partition
ORDER BY num_files DESC, avg_size ASC;

-- ② Which manifests are below average size? Feed these to rewrite_manifests.
WITH avg_len AS (SELECT AVG(length) AS a FROM glue_catalog.silver_db.orders.manifests)
SELECT path, length FROM glue_catalog.silver_db.orders.manifests
WHERE length < (SELECT a FROM avg_len);

-- ③ Which snapshots contain deletes? These are the ones to expire for real GDPR erasure.
SELECT added_snapshot_id FROM glue_catalog.silver_db.orders.manifests
WHERE deleted_data_files_count > 0;
Spark SQL · the maintenance setschedule these, filtered
-- Expire: older than 90 days, but always keep the most recent 100 snapshots
CALL glue_catalog.system.expire_snapshots(
  table => 'silver_db.orders',
  older_than => TIMESTAMP '2026-06-01 00:00:00.000',
  retain_last => 100,
  max_concurrent_deletes => 8,
  stream_results => true);        -- avoids driver OOM on huge deletions

-- Expire ONE snapshot — e.g. you accidentally committed sensitive data
CALL glue_catalog.system.expire_snapshots(
  table => 'silver_db.orders', snapshot_ids => ARRAY(8333017788700497002));

-- Manifests
CALL glue_catalog.system.rewrite_manifests('silver_db.orders');

-- Orphans — ALWAYS dry run first, then drop the flag
CALL glue_catalog.system.remove_orphan_files(
  table => 'silver_db.orders', dry_run => true);
write.metadata.metrics.column.*

Stop collecting stats you never use

Default is truncate(16) per column. On a 100+ column table that metadata becomes a burden — set none or counts on columns nobody filters, full on the ones they do.

write.object-storage.enabled

Defeat S3 prefix throttling

Injects a hash into the path so files in one partition no longer share a prefix. On big partitions this is the difference between throughput and 503s.

write.distribution-mode

Stop making small files at write time

none is arbitrary — 10 rows for one partition spread over 10 tasks becomes 10 files. hash distributes by partition key; range by sort order.

12Catalogs

Six ways to store one pointer

A catalog does exactly one job: map db.table to the path of its current metadata file. Everything that distinguishes them is where they keep that string and whether they can update it atomically. The second requirement is the one that separates a dev toy from a production catalog.

catalogproductionpointer stored asmulti-table txnsthe catch
HadoopNoversion-hint.text / dir listingNoNo atomic rename on S3 → data loss under concurrent writes
HiveYeslocation propertyNoYou operate the Metastore (EMR can host it)
AWS GlueYesmetadata_locationNoAWS-only; awkward in multicloud
NessieYesmetadataLocationYesSelf-hosted; narrower engine support
RESTYesimplementation-definedYesAn interface — you supply or buy the backend
JDBCYesmetadata_location in the DBNoEvery engine must ship a JDBC driver

Two config styles follow from that table, and mixing them up is the most common setup error: shorthand catalogs use type=hadoop|hive|rest, while class-backed catalogs (Glue, Nessie, JDBC) use catalog-impl=<fully-qualified class> and no type at all.

13Branches, tags & write-audit-publish

Never let unvalidated data reach production

A branch is a named, mutable pointer to its own chain of snapshots; a tag is an immutable one. Together they let you do the thing every data team wants and few achieve: write into the real table, audit it there, and publish only if it passes — with no staging table, no data copy, and no window where bad rows are visible.

PySpark · the full WAP cyclebranch-based; works on EMR + Glue Catalog
# ① branch off the current state of the production table
spark.sql("ALTER TABLE glue_catalog.silver_db.orders CREATE BRANCH etl_branch")

# ② turn WAP on for the table, then bind THIS SESSION to the branch
spark.sql("""ALTER TABLE glue_catalog.silver_db.orders
             SET TBLPROPERTIES ('write.wap.enabled'='true')""")
spark.conf.set('spark.wap.branch', 'etl_branch')     # reads AND writes now go to the branch

# ③ run the unchanged production ETL — it lands on the branch
spark.sql("INSERT INTO glue_catalog.silver_db.orders SELECT * FROM new_data")

# ④ prove the isolation held
spark.sql("SELECT count(*) FROM glue_catalog.silver_db.orders VERSION AS OF 'etl_branch'").show()
spark.sql("SELECT count(*) FROM glue_catalog.silver_db.orders VERSION AS OF 'main'").show()

# ⑤ audit — nulls, duplicates, ranges
df = spark.table("glue_catalog.silver_db.orders")
df.select([count(when(col(c).isNull(), c)).alias(c) for c in df.columns]).show()
dupes = df.groupBy(df.columns).count().filter(col("count") > 1).drop("count")

# ⑥ publish: move the validated snapshot onto main. Metadata only — no data moves.
snap = spark.sql("""SELECT snapshot_id FROM glue_catalog.silver_db.orders.refs
                       WHERE name = 'etl_branch'""").first()[0]
spark.sql(f"CALL glue_catalog.system.cherrypick_snapshot('silver_db.orders', {snap})").show()

# ⑦ release the session — otherwise the next job still writes to the branch
spark.conf.unset('spark.wap.branch')
Four ways to move the pointer

Rollback vs. set vs. cherry-pick

  • rollback_to_snapshot / rollback_to_timestamp — back to a snapshot in this table's history; non-destructive, safe to run concurrently
  • set_current_snapshot — to any snapshot, including one on another branch or tag
  • cherrypick_snapshot — creates a new snapshot applying another one's changes; single commit only
Tags

Reproducibility you can name

A tag freezes a snapshot behind a human name, with its own retention. Quarter-end closes, model training sets, the state a report was published from — anything you may need to reproduce exactly.

ALTER TABLE …orders
  CREATE TAG 'Q3FY26_close'
  AS OF VERSION 8
  RETAIN 14 DAYS;
14Migration

Into Iceberg: keep the files, or rewrite them

Two strategies, and the choice is really about risk appetite. In-place migration writes new Iceberg metadata around your existing Parquet — nothing is copied, so it's fast and cheap, but there's no easy undo. Shadow migration writes a brand-new table and cuts over in phases — more storage, more time, and you can walk away from it at any point.

procedurewhat it createsthe source table afterwardsreach for it when
snapshot()A temporary Iceberg table over the same data filesStill fully usable — Hive and Iceberg coexistYou want to test Iceberg against real data with zero risk
migrate()An Iceberg table replacing the source, copying schema, partitioning, properties and locationHive access path is gone — it is an Iceberg table now (optional backup namespace, removable with drop_backup)The real production cutover, once testing passed
add_files()Nothing — imports files into an existing Iceberg tableUntouched, but the files are now also owned by IcebergLoose Parquet with no metastore, or incremental per-partition import
Spark SQL · the three migration proceduresnone of them copy data
-- Test drive: Hive table stays alive, you get an Iceberg twin over the same files
CALL glue_catalog.system.snapshot('hive.db.orders', 'silver_db.orders_test');

-- Commit: the table becomes Iceberg. There is no going back through Hive.
CALL glue_catalog.system.migrate('hive.db.orders', map('write.format.default', 'parquet'));

-- Incremental: pull ONE partition of loose Parquet into an existing Iceberg table
CALL glue_catalog.system.add_files(
  table                 => 'silver_db.orders',
  source_table          => '`parquet`.`s3://lake/legacy/orders`',
  partition_filter      => map('dt', '2026-08-31'),
  check_duplicate_files => true);
RISK
add_files does not validate schema — files that don't match the target table's schema and partitioning produce silently wrong reads. Worse, once imported, later Iceberg operations can physically delete those files. Never point it at a directory another live system still owns.
15Streaming

Every micro-batch is a commit

Structured Streaming into Iceberg works exactly as you'd hope — and that is the problem. Each micro-batch commits a snapshot, so a one-second trigger produces 86,400 snapshots and a blizzard of tiny files per day. Streaming Iceberg is a tuning exercise between three dials: trigger interval, fanout, and compaction.

PySpark · stream in, stream outcheckpointLocation is mandatory
# ---- WRITE a stream INTO an Iceberg table -------------------------------
(events
  .writeStream
  .format("iceberg")
  .outputMode("append")                          # or "complete" to replace each batch
  .trigger(processingTime="1 minute")             # ← the commit-rate dial
  .option("path", "glue_catalog.silver_db.orders")
  .option("fanout-enabled", "true")               # partitioned target: skip the sort requirement
  .option("checkpointLocation", "s3://lake/_checkpoints/orders")
  .start())

# ---- READ a stream FROM an Iceberg table (append snapshots only) --------
df = (spark.readStream
        .format("iceberg")
        .option("stream-from-timestamp", str(start_ms))
        .load("glue_catalog.silver_db.orders"))

# ---- and the maintenance that makes it survivable -----------------------
# run hourly, scoped to the hour just completed
spark.sql("""CALL glue_catalog.system.rewrite_data_files(
     table   => 'silver_db.orders',
     strategy=> 'binpack',
     where   => 'order_ts >= current_timestamp() - INTERVAL 1 HOUR',
     options => map('partial-progress-enabled','true'))""")
16Running it on AWS

The wiring: EMR, Glue Catalog, S3

Every configuration in this atlas comes down to four properties: load the runtime, register the SQL extensions, point a catalog name at an implementation, and tell it which S3 prefix is the warehouse. Get those right and the rest of the format is just SQL.

PySpark · EMR + Glue Catalogthe session every example in this atlas assumes
import pyspark
from pyspark.sql import SparkSession

conf = (pyspark.SparkConf().setAppName('iceberg_on_emr')
  # ① the runtime — MUST match your Spark and Scala versions
  .set('spark.jars.packages',
       'org.apache.iceberg:iceberg-spark-runtime-3.5_2.12:1.10.0')
  # ② the SQL extensions — CALL procedures, ALTER … PARTITION FIELD, WRITE ORDERED BY
  .set('spark.sql.extensions',
       'org.apache.iceberg.spark.extensions.IcebergSparkSessionExtensions')
  # ③ name a catalog and back it with Glue
  .set('spark.sql.catalog.glue_catalog', 'org.apache.iceberg.spark.SparkCatalog')
  .set('spark.sql.catalog.glue_catalog.catalog-impl',
       'org.apache.iceberg.aws.glue.GlueCatalog')
  # ④ where the bytes go, and how to talk to S3
  .set('spark.sql.catalog.glue_catalog.warehouse', 's3://my-lakehouse/warehouse/')
  .set('spark.sql.catalog.glue_catalog.io-impl',
       'org.apache.iceberg.aws.s3.S3FileIO')
  # sensible defaults for any real job
  .set('spark.sql.adaptive.enabled', 'true')
  .set('spark.sql.session.timeZone', 'UTC'))

spark = SparkSession.builder.config(conf=conf).getOrCreate()
AWS Glue ETL job

Two job parameters

Set --datalake-formats to iceberg, then pass the same four catalog settings through --conf. Watch for line breaks silently swallowing a setting.

Local laptop

Same code, one flag

Swap catalog-impl for type=hadoop and point warehouse at a local path. Not one line of the example SQL changes — which is exactly the promise the format makes.

Version matching

The one that bites

The runtime artifact encodes both Spark and Scala versions. A mismatch fails with IncompatibleClassChangeError at session start, not at query time — check the Iceberg compatibility matrix first.
