01 · The platform

One lake, one catalog, three engines

Nothing on AWS "contains" your data warehouse. The data is one copy of Parquet/Iceberg files in S3; the Glue Data Catalog is the shared phone book; and three interchangeable engines borrow both. The split to teach: metadata plane (ask the catalog where the table lives) vs data plane (read S3 directly, at full parallelism).

02 · Inside the cluster

Anatomy of an EMR cluster

Three node roles, and the role decides what is safe to lose. The primary node schedules; core nodes compute and hold HDFS + shuffle files; task nodes only compute — which is exactly why task nodes go on spot and core nodes don't. The data itself never lives on the cluster: S3 is storage, the cluster is compute.

EMR on EC2

You own the cluster

Full spark-defaults.conf, YARN, GC flags, custom AMIs. Cheapest per TB, highest ops. 5–10 min startup.

EMR Serverless

Submit, capacity appears

Choose vCPU / memory per worker, open-source Spark confs, seconds to start. Cheaper than Glue, no cluster to babysit.

Spark as pods

For shops already running Kubernetes — Spark jobs share the existing EKS cluster and its tooling.

03 · Under your Python

Python holds the wheel. The JVM drives.

Your PySpark script does zero row processing. Py4J carries a few kilobytes of plan across a local socket into the JVM, where Catalyst rewrites it and Tungsten compiles it. Your 1 TB never enters a Python process — unless you write a Python UDF, which forces every one of 1.4 billion rows across that boundary.

04 · The 1 TB question — step 1

Waves: the data streams past the cores

The sharp student asks: "64 cores, 1 TB — every subtotal a core computes is intermediate, so how does the cluster converge without one machine holding everything?" Step one of the answer: nobody holds the terabyte. The driver cuts it into ~8,000 tasks of ~128 MB and the cores consume them in 125 sequential waves, discarding raw rows as they go.

1 TB = 1,024,000 MB ÷ 128 MB = 8,000 tasks ÷ 64 cores = 125 waves
live memory at any moment = 64 × 128 MB ≈ 8 GB — not one terabyte.
05 · The 1 TB question — step 2

The shrinker: map-side partial aggregation

A core does not ship its million raw rows anywhere. It keeps a tiny in-memory hash map — one running sum per department — and emits ~50 subtotal rows per slice. The shuffle is expensive, so Spark makes sure the thing being shuffled is tiny. This is the whole trick.

06 · The 1 TB question — step 3

The hash shuffle: routing by key

Thousands of subtotals now sit scattered across four nodes. To finish, every subtotal for a key must meet. Spark doesn't search — every record computes its own address with the same deterministic function, so all the Grocery subtotals in the cluster land on the same reducer without anyone coordinating.

Where a reducer lives · 1

A task, not a machine

"Reducer 7" = shuffle partition 7, processed by a task inside an executor JVM. You get spark.sql.shuffle.partitions reducers (200 by default) — not one per node. On 10 nodes × 8 cores, the 200 reduce tasks run across 80 cores in ~3 waves, exactly like chapter 04.

Where a reducer lives · 2

The mailbox is local disk — never HDFS

Each map task writes its hashed output as shuffle files on its own node's local disk (spark.local.dir) — plain Spark-managed files. On EMR core nodes they share physical disks with HDFS blocks, but HDFS plays no role in a shuffle. Reducers fetch their partition from every node over the network.

Where a reducer lives · 3

Math in memory, disk as parachute

The reduce task merges its fetched blocks in executor JVM memory (spark.executor.memory), spilling to local disk only if the partition outgrows it. Here: ~200 MB ÷ 200 reducers ≈ 1 MB each — pure RAM. Skew (ch 09) is when one partition blows past memory and grinds through spills.

07 · The 1 TB question — step 4

Why the local answer is the global answer

Reducer 7 owns 100% of the Electronics subtotals that exist anywhere in the terabyte. Not most — all. So its local sum is not intermediate; it is the true global answer, computed on a machine that never held more than a few megabytes. No coordination round. No second pass. No central assembler.

what it cost → one pass over S3 · one network exchange of ~200 MB · zero full-dataset materialisation
on 64 cores: minutes, not hours — and the number is exact.
08 · The 1 TB question — step 5

Global sort without a global sorter

"Fine for sums — but ORDER BY is different. How can the whole thing be sorted when each machine sees a slice?" Spark swaps the routing rule: range partitioning instead of hash. Sample the data, cut it into value bands, give each reducer one contiguous band — then local sorts stitch together already in order.

09 · The 1 TB question — step 6

Skew: the routing rule concentrates the pain

The same rule that guarantees correctness — all of a key's records reach one machine — is the rule that hurts when a key is huge. If 60% of rows are region = 'NA', one reducer receives 60% of the shuffle. 199 reducers finish in seconds; the stage ends when the last one does.

10 · The write

Iceberg: the atomic pointer swap

S3 has no atomic rename — classic Hive-style writes copy 200 GB twice and can leave readers a half-written table. Iceberg writes data files once, to their final location, and controls visibility with a metadata pointer swapped atomically in the Glue Catalog. Readers see the old snapshot, then the new one. Never anything in between.

11 · Consequence

The four knobs, and the board takeaway

Out of hundreds of Spark configurations, these four are the ones you will actually touch — and the 200-partition default is the single most common misconfiguration in production Spark.

configurationdefaultwhat it controlswhen to change it
spark.sql.files.maxPartitionBytes128 MBhow S3 files are cut into input partitions on read (the "waves" slice size)Rarely. Raise for huge files + idle cores; lower for heavy per-row work.
spark.sql.shuffle.partitions200how many partitions come out of every shuffle (the % 200 in chapter 06)Often. 200 was chosen for 2015 laptops. Set 2–4× your core count — frequently a 2–3× speedup for one line.
spark.sql.adaptive.enabledtrue (3.x)AQE — re-optimises at runtime: coalesces small partitions, splits skewed ones, converts joins to broadcastLeave it on. Verify it is on. It fixes most of chapter 09 automatically.
spark.sql.autoBroadcastJoinThreshold10 MBbelow this size, the small side of a join is broadcast — the whole shuffle disappearsRaise to 50–200 MB when dimension tables outgrow 10 MB and executors have RAM to spare.
⚠️
A 1 TB aggregation into 200 partitions = 200 tasks of ~1 GB each. With 320 cores, 120 sit idle while the rest chew oversized partitions and spill to disk. Notice what's not on any fix list: buying a bigger cluster — the most expensive way to hide a layout problem.

The lecture takeaway, for the board

  1. Waves — cores stream 128 MB slices; raw rows are discarded immediately. 1 TB needs ~8 GB of live memory, not 1 TB.
  2. Map-side combine — a terabyte becomes megabytes before it touches the network.
  3. Hash routing — all records for key X reach the same worker, so its local answer is the global answer.
  4. Range routing — sorted bands stitch together in order: globally sorted, with no global sorter.
  5. The commit — data files first, manifests second, pointer last. Visibility is one atomic swap.
